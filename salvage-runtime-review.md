# Runtime, tools and memory salvage review

This is a focused source review for the proposed Python background service, not a claim that all runtime files were individually audited or that their behavior has been verified by execution. Existing implementations are TypeScript and closely coupled to Aiden. Suggested dispositions describe value to Milo, not permission to copy code without license review. No files were deleted in this review.

## Lower priority and product-dependent areas

- `core/v4/a2a/`, `core/v4/subagent/`, `tools/v4/subagent/`: multi-agent delegation is not needed to prove the first single-agent service. Preserve as reference until Milo's delegation policy is chosen.
- `core/v4/mcp/`, `tools/v4/mcpImport.ts`, `tools/v4/mcpSetup.ts`, `core/v4/plugins/`, `core/v4/integrations/`, `core/v4/daemon/triggers/`: optional external tools and channels can be valuable later, but introduce separate trust, credential and lifecycle concerns. Retain for assessment.
- `core/v4/codebase/`, `core/v4/coding/`, `core/v4/browser/`: potentially valuable for specific capabilities; retain until the initial tool scope is chosen. Do not imply these handlers work unchanged in Python.
- `core/v4/voice/`, `core/v4/theme/`, `core/v4/ui/`, `core/v4/presence/`: product/UI-specific references; defer until product feature decisions.
- `core/v4/daemon/taskStore.ts`, `cron/` and `daemon/cron/`: older/parallel task and scheduling surfaces may duplicate newer authorities. Keep for compatibility analysis until one Milo task and schedule model is chosen; no automatic schema migration is assumed.
- `core/v4/daemon/db/`: inspect schema, migrations and transactional behavior as references. Do not copy the entire Aiden database or import old migrations into a fresh Milo database by default.

## Aiden-specific candidates for retirement, not proven useless

`core/v4/update/` implements parts of Aiden install/update handling, including npm/Windows paths; `core/v4/commercial/`, `core/v4/license/` and `moat/proLicense.ts` contain Aiden-specific commercial/licensing implementation. Their product-specific source and tests are unlikely to be direct Milo runtime components. However, the current Node runtime imports some of them, so deletion would break that reference runtime. Preserve them until the parent decides whether keeping Aiden runnable matters and checks dependencies; extract general update/security requirements before removal. `core/v4/daemon/templates/systemd.service.template` is Linux-specific and not necessary for a macOS-first launch, but could inform later platforms. These are candidates, not recommendations to delete immediately.

## Licensing and verification

The inspected core files include AGPL-3.0 notices and the root package identifies AGPL-3.0-only. `LICENSE-SKILLS.md` separately describes Apache-2.0 terms for the skills directory and certain scaffolding. A translation can be a derivative work; record provenance and obtain appropriate license review before copying or translating. Tests and third-party dependencies also need review. This assessment used static inspection; it did not execute the service or verify every source file.
