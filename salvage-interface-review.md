# Interface and provider salvage review

Scope: source inspection of `cli/`, `dashboard-next/`, `electron/`, `api/`, `providers/v4/` and related npm entry points. These are proposed migration decisions, not proof that every individual file has been audited. No files were deleted in this review. Core implementation is marked AGPL-3.0-only; inspect licenses and asset provenance before reuse or translation.

## Old release path: disable or remove from Milo distribution

The user explicitly does not want the Aiden npm download as Milo's product. The root package retains the inherited name `aiden-runtime`, but is now private and no longer exposes npm commands. The secondary launcher is also private and no longer registers commands. `bin/aiden-bootstrap.cjs` hardcodes the old package and npm registry, checks installed compiled Aiden files and invokes its updater. `bin/aiden-updater.cjs`, `cli/v4/commands/update.ts`, `cli/v4/updateBootPrompt.ts`, `core/v4/update/` and `scripts/postinstall.js` carry additional Aiden-specific install/update behavior; `cli/v4/envSources.ts` recognizes the old package identity. `dashboard-next/package.json` and Electron packaging remain Aiden application build configurations. Changing only README instructions or removing one executable alias does not remove all paths. Review manifest, updater entry points, release scripts and references together; avoid shipping a `milo` alias that invokes Aiden.

These are removal candidates from the **new product's build and distribution**, but parts remain useful as references until new packaging/update behavior and tests exist. Deleting source prematurely can break old tests/build references; there is no reason to preserve its installation as a supported Milo interface. A separate existing public npm package, if any, cannot be unpublished or changed by edits in this checkout.

## Replace / defer rather than port wholesale

- `electron/` is Electron-specific, and `electron/main.js` expects a standalone dashboard server while `dashboard-next/next.config.js` configures static export. Do not treat it as a finished macOS app. Its preload API and updater belong to the old shell.
- `api/server.ts`, `api/dashboard.ts`, `api/entry.ts`, `api/mcp.ts`, and `api/routes/computerUse.ts` are Express/legacy API entry points tied to older runtime and Node services. Inventory behavior and security tests before retiring; do not expose them as the Python service without redesign.
- `cli/aiden.ts`, `cli/v4/aidenCLI.ts`, `daemonAgentBuilder.ts`, `commands/`, frame and onboarding code assemble or control the TypeScript runtime. Their whole implementation is not a drop-in Milo client. Retain task, terminal and interruption behavior references; defer channels, billing, cloud auth, integrations and old updater paths unless Milo explicitly adopts them.
- Provider adapters (`chatCompletionsAdapter.ts`, `messageApiAdapter.ts`, `responseStreamAdapter.ts`, `localPromptToolsAdapter.ts`) are optional backend integration references; `runtimeResolver.ts`, `registry.ts`, `modelCatalog.ts`, and credential files are coupled to existing provider metadata. Keep as reference until backend support and credential policy are decided, rather than claiming they form the requested inference engine.
- `dashboard-next/components/PricingModal.tsx`, `AccountSetupPanel.tsx`, `MessagingSetupPanel.tsx`, `publicSponsors.ts`, Aiden branding (`AidenMark.tsx`, `public/brand/aiden-logo.png`) and connection setup are inherited product-specific material. Do not include in the Milo app by default; defer or retire after assessing any reusable behavior and asset rights. `public/brands/NOTICE.txt` must accompany any retained third-party brand assets.
- `dashboard-next/scripts/copy-standalone-assets.js` and Next build configuration reflect the old dashboard delivery pipeline. Evaluate if a React static frontend is reused in Tauri; they are not the planned website or a macOS app packaging solution.

## Verification needed

Before deleting specific files, inspect imports, package scripts, release automation, tests, generated files and required historical attribution. When the old install path is disabled, verify no new Milo artifact installs or updates from Aiden npm or invokes the old bootstrap; this cannot disable the upstream registry package. Build and test the new app/service/CLI once they exist, including authenticated multi-client connection, service startup, cancellation and version mismatches. This review did not run the old UI or establish its current build health.
